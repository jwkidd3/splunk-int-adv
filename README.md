# Splunk Intermediate / Advanced

An eighteen-module Splunk course with sixteen hands-on labs, built around
**Harborview Outfitters** — a fictional outdoor equipment retailer whose data
is generated by a script in this repository.

Everything here is original to this course and licensed under Apache 2.0.
There is no vendor courseware, no vendor sample data and no third-party
conference material.

**The whole course runs offline, and no lab or demonstration requires a
third-party app.** Nothing is downloaded from Splunkbase. The one thing to
stage before you travel is the Splunk container image itself.

The course data, the lookups, the field extractions and the data models are
all committed here, along with the local service Lab 11 needs.

## Before class (needs internet, once)

### 1. Save the Splunk image

```bash
docker pull splunk/splunk:10.4.3
```

```bash
docker save splunk/splunk:10.4.3 -o splunk-image.tar
```

Copy `splunk-image.tar` to the classroom machines alongside this repository.
Pin a version — `latest` moves, and a course does not.

### That is the only thing

Module 14 covers the Common Information Model, which Splunk publishes as a
Splunkbase add-on. **This course does not install it.** It ships two small
data models of its own instead — `Harborview_Web` and
`Harborview_Authentication` — already mapped onto CIM field names, so
`| datamodel` and `| tstats` run on the class instance with nothing
downloaded. Students learn the convention, which is the part that transfers
to a production system.

## Classroom setup (no internet)

### 1. Generate the data

```bash
python3 tools/generate_data.py
```

Timestamps are written relative to **the moment you run it**, so the labs'
"Last 24 hours" and "Last 7 days" ranges land on real events. Run it the
morning of class. Standard library only, no packages to install.

```
--days 30     how far back events reach
--seed 1729   change only if you want a different dataset
--out DIR     write somewhere other than data/
```

The seed makes it deterministic, so every student gets identical data and
every answer key stays correct.

### 2. Start Splunk

```bash
docker load -i splunk-image.tar
```

```bash
docker run -d -p 8000:8000 --platform linux/amd64 -e SPLUNK_GENERAL_TERMS=--accept-sgt-current-at-splunk-com -e SPLUNK_START_ARGS=--accept-license -e SPLUNK_PASSWORD=password --name splunk splunk/splunk:10.4.3
```

`SPLUNK_GENERAL_TERMS` is required — current images refuse to start without
it. Splunk comes up on <http://localhost:8000> as `admin` / `password`.

### 3. Create the class app

Labs 8, 10 and 11 name this app explicitly. Settings > Apps > Create app:

| Field | Value |
| ----- | ----- |
| Name | `CLASS: Intermediate` |
| Folder name | `splunk_intadv` |
| Visible | Yes |

The folder name appears in every **Destination app** dropdown; the display
name is what the labs mean by "return to the class app".

### 4. Create the indexes

Settings > Indexes > New Index, five of them:

`web` · `security` · `sales` · `network` · `apps`

### 5. Load the data

The quickest route is the loader, which does sections 5 to 7 in one go:

```bash
tools/load_data.sh
```

It creates the indexes, installs `conf/` as a Splunk app, copies the lookup
CSVs into it, and one-shots every file with the right index, sourcetype and
host. It is idempotent — it empties the indexes first, so re-running does not
double your event counts. Pass `--append` if you want to add instead.

To do it by hand instead, the rest of this section and sections 6 and 7
describe the same work through the UI.


| Index | Sourcetype | host | File |
| ----- | ---------- | ---- | ---- |
| `web` | `access_combined` | segment in path 2 | `data/access.zip` |
| `security` | `linux_secure` | segment in path 2 | `data/secure.zip` |
| `sales` | `vendor_sales` | `appserver` | `data/vendor_sales.log` |
| `sales` | `sales_entries` | `appserver` | `data/sales_entries.json` |
| `network` | `web_proxy` | `proxy` | `data/web_proxy.json` |
| `network` | `firewall` | `firewall` | `data/firewall.json` |
| `apps` | `trailmate_beta` | `appserver` | `data/trailmate_beta.log` |

Both archives unzip to `<name>/<host>/<name>.log`, so **segment 2** of the
path gives the host. `access.zip` yields `www1`, `www2`, `www3`;
`secure.zip` adds `mailsv`.

Load `trailmate_beta.log` with **no** field extraction — Lab 7 is where
students build it.

Verify everything landed:

```
| eventcount summarize=false index=* | dedup index | table index count
```

> **The configuration in `conf/` is not optional.** A stock Splunk recognises
> the `linux_secure` sourcetype but ships none of its field extractions —
> those live in the Splunk Add-on for Unix and Linux, which is a Splunkbase
> download. Without `conf/props.conf`, `src_ip`, `user` and `vendor_action`
> resolve to nothing and seven of the twelve labs return empty results with no
> error to explain why. If you load by hand, install `conf/props.conf` and
> `conf/transforms.conf` into the class app's `local/` directory and put the
> lookup CSVs in its `lookups/` directory.

### 6. Create the lookups

Settings > Lookups. Upload each file, add a definition, then an **automatic**
lookup bound to the sourcetype.

| Sourcetype | File | Match on |
| ---------- | ---- | -------- |
| `access_combined` | `data/products.csv` | `productId` |
| `vendor_sales` | `data/products.csv` | `Code` |
| `vendor_sales` | `data/vendors.csv` | `VendorID` |

These supply `product_name`, `categoryId` and `price` to the store data, and
`VendorCountry` / `VendorStateProvince` to the retail data. Labs 2, 3, 4, 5,
10 and 12 all depend on them.

Share them to the app, not to yourself. Lab 6 step 19 explains why in detail:
a private automatic lookup silently returns nothing for everyone else, with no
error to diagnose.

### 7. One more lookup, for Lab 12

Upload `data/http_status.csv` into **Search & Reporting** and create a
file-based lookup definition named exactly **`http_status_lookup`**. No
automatic lookup — Lab 12 wires it into the data model by hand.

Its columns are `code` and `description`, which is why Splunk's built-in
`http_status.csv` will not do: that one uses `status` and `status_description`.

### 8. Start the local endpoint, before Lab 11

```bash
python3 tools/ip_lookup_server.py
```

Lab 11 builds workflow actions that hand a source address to a web service.
This is that service, running on `http://127.0.0.1:8888`. Leave it up for the
lab. Link actions open in the student's own browser, so `127.0.0.1` is correct
even with Splunk in a container.

## The presentations

Fourteen self-contained Reveal.js decks in [`presentations/`](presentations/).
Each is a single HTML file with the framework inlined — open one from disk and
it works, with no server and no network.

To change content, edit `tools/course_content.py` and rebuild:

```bash
python3 tools/build_presentations.py
```

```
--only 3 7    rebuild just those modules
--out DIR     write elsewhere
```

Content and styling are separate on purpose: the renderer in
`build_presentations.py` holds the CSS and layout once, so fourteen decks stay
consistent instead of drifting apart as fourteen hand-edited copies would.

Press **S** in any deck for speaker notes, **O** for the slide overview,
**F** for full screen.

## The scenario

**Harborview Outfitters** sells outdoor equipment through
`harborviewoutfitters.example` and a network of retail vendors in eleven
countries. Three web servers, a proxy, a firewall, and a mobile app in beta.

Fourteen products across five categories — TENTS, PACKS, FOOTWEAR, NAVIGATION,
APPAREL — and thirty-two vendors whose `VendorID` encodes their region:

| Range | Region |
| ----- | ------ |
| 1000–2999 | United States |
| 3000–3999 | Canada |
| 4000–4999 | Latin America |
| 5000–6999 | Europe & Middle East |
| 7000–8999 | Asia Pacific |
| 9000–9900 | Africa |
| 9901–9999 | Outliers |

Labs 2 and 3 rely on those ranges, so keep them if you edit the generator.

## Notes for the instructor

- **Regenerate the data the morning of class.** It is the single thing that
  most affects whether labs work as written.
- **Lab 1 is about method, not answers.** Students should leave able to open
  the Job Inspector and say which phase is expensive.
- **Lab 6 has no SPL** and is easy to rush. It is the lab that makes Modules 8
  to 13 make sense.
- **Lab 12 is the longest.** Budget accordingly, and have students build it in
  Search & Reporting, not the class app.
- **Modules 15 to 18 are the advanced block.** They assume everything before
  them. Labs 15 and 16 are mostly UI and administration rather than SPL, and
  Lab 15 has students sign in as a restricted user they create — have them
  use a private browser window so they keep their admin session.
- **Lab 16 searches `_internal` and `_audit`**, Splunk's own indexes rather
  than course data. Those exist on any instance, so the searches work
  regardless of what you loaded, but the numbers will be specific to your
  container.
- **Module 14 needs nothing installed.** Its `datamodel` and `tstats`
  demonstrations run against `Harborview_Web` and
  `Harborview_Authentication`, which `tools/load_data.sh` installs. On a
  production system you would point the same commands at the CIM add-on's
  models instead.
- Field *names* are case sensitive throughout Splunk; field *values* are not,
  except in `where` and in lookup matches. This trips up at least one student
  per class, which is why Lab 1 opens with it.
- **Check the labs still run before class:**

  ```bash
  python3 tools/validate_labs.py
  ```

  It executes every complete search in `labs/` against the live instance and
  exits non-zero if any returns nothing. Searches that are *supposed* to be
  empty — the case-sensitivity contrast in Lab 1, anything depending on an
  object the student has not created yet — are listed in the script with the
  reason, so a failure means something is genuinely wrong.
- **Install the course config into its own app, not `etc/system/local`.**
  System-level configuration is shadowed by any app defining the same object.
  On a shared training instance that is a real collision: another course's
  `products_lookup` will silently win, and your searches will enrich with its
  data instead of yours.
